= Appendix: MCP Gateway

include::partial$console-access.adoc[]

So far, the intelligent assistant has talked to MCP servers one at a time: the built-in OpenShift MCP server from the cluster interaction module, and the custom Insights MCP server you registered yourself. That works fine for a couple of servers, but it does not scale. Every AI client has to know the address of every server, credentials have to be negotiated with each one, and there is no single place where the platform team can see or control what the LLM is actually allowed to do.

This is the problem the **MCP Gateway** solves. Instead of connecting OpenShift Lightspeed to each MCP server individually, you route all MCP tool calls through a single, centrally managed gateway endpoint. The gateway aggregates every registered MCP server behind one URL, so from the perspective of OpenShift Lightspeed — or any other MCP client — the gateway is just a single MCP server. Behind that front door, the platform team can apply consistent controls to every tool call:

* **Federation** — register as many MCP servers as you need behind one endpoint and one tool catalog; every server's tools are namespaced with a prefix so they never collide.
* **Authentication** — validate *who* is calling on every tool call, using the cluster's own identity infrastructure.
* **Authorization** — decide *which tools* each user or group may call, with ordinary Kubernetes RBAC.
* **Rate limiting** — give every identity its own quota, so a runaway agent cannot starve the MCP servers.
* **Tracing** — distributed traces of every tool call, from the client through the gateway to the server.
* **Guardrails** — content inspection of every tool call and tool response, blocking PII leakage or prompt injection.

The recommended full stack for MCP security and governance includes:

* **Red Hat OpenShift AI** provides the MCP Lifecycle operator that manages MCPServer resources, the MCP catalog, and TrustyAI to enforce MCP guardrails.
* **Connectivity Link** provides the Gateway API infrastructure and the Kuadrant policy engines.
* The **MCP server for Red Hat OpenShift** provides the cluster tools, deployed as a managed MCPServer resource so the gateway can federate it.

== 1. Install Red Hat OpenShift AI

The first building block is Red Hat OpenShift AI. It covers the three pieces the gateway stack needs: the MCP Lifecycle operator that manages MCPServer resources, the MCP catalog you will deploy the MCP server from, and the TrustyAI component that provides the guardrails around your MCP servers.

Red Hat OpenShift AI is not yet published in the `redhat-operators` catalog on OpenShift 5. Add a snapshot of the 4.22 Red Hat Operators catalog in your cluster instead:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: operators.coreos.com/v1alpha1
kind: CatalogSource
metadata:
  name: redhat-operators-snapshot
  namespace: openshift-marketplace
spec:
  sourceType: grpc
  image: quay.io/rhpds/olm_snapshot_redhat_catalog:v4.22_2026_11_11
  displayName: Red Hat Operators (4.22 Snapshot)
  publisher: Red Hat AgnosticD
  priority: -500
  grpcPodConfig:
    extractContent:
      cacheDir: /tmp/cache
      catalogDir: /configs
    memoryTarget: "30Mi"
    securityContextConfig: restricted
EOF
----

Wait for the catalog to be ready:

[source,bash,role="execute"]

oc wait catalogsource/redhat-operators-snapshot -n openshift-marketplace \

[#deploy-mcp-server]
== 2. Deploy the MCP server for Red Hat OpenShift

The gateway needs something to federate. This module deploys the MCP server for Red Hat OpenShift — the same server that powered cluster interaction in OpenShift Lightspeed — but this time as a managed MCPServer resource deployed from the MCP catalog, so the MCP Lifecycle operator takes care of running it.

First, the supporting resources: the namespace, a service account, RBAC, and the server's configuration. The service account is bound to the standard `edit` cluster role, which grants read and write access to cluster resources: the write tools can create, update, and delete workloads. Finally, the ConfigMap states which MCP toolsets will be enabled. In this case, the same tools as the OpenShift Lightspeed built-in server, plus `netedge` and `ossm`:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: mcp-servers
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: openshift-mcp-server
  namespace: mcp-servers
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: openshift-mcp-server-edit
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: edit
subjects:
  - kind: ServiceAccount
    name: openshift-mcp-server
    namespace: mcp-servers
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: openshift-mcp-server-config
  namespace: mcp-servers
data:
  config.toml: |
    log_level = 5
    port = "8080"
    toolsets = ["core", "config", "observability/metrics", "netedge", "ossm"]
    cluster_auth_mode = "kubeconfig"
    read_only = false
    disable_destructive = false
EOF
----

Now deploy the server itself from the catalog. In the OpenShift AI web console:

* Open *AI hub* > *MCP servers*
* Open the Catalog tab
* Open the *Red Hat OpenShift MCP server* entry
* Click *Deploy MCP server*.
* In the deployment dialog, enter `openshift-mcp-server` as the name, then select project `mcp-servers`.
* In the generated YAML, confirm that the ConfigMap name is openshift-mcp-server-config and under runtime.security.serviceAccountName set `serviceAccountName: openshift-mcp-server`. The YAML configuration should look like:
+
[source,yaml]
----
runtime:
  security:
    serviceAccountName: openshift-mcp-server
config:
  port: 8080
  path: /mcp
  arguments:
    - '--config'
    - /etc/mcp-config/config.toml
  storage:
    - path: /etc/mcp-config
      source:
        type: ConfigMap
        configMap:
          name: openshift-mcp-server-config
----
* Then click *Deploy*.
* Wait for the Status of the deployment to show _Available_.

Back in the bastion, wait for the MCP server to be ready:

[source,bash,role="execute"]
----
oc wait --for=condition=Ready mcpserver/openshift-mcp-server -n mcp-servers --timeout=600s
----

The catalog records the deployment in the model registry, so the MCP servers dashboard shows the server's status, and the MCP Lifecycle operator manages its lifecycle — upgrades, configuration, and health — from now on.

[#install-connectivity-link]
== 3. Install Connectivity Link

Connectivity Link is Red Hat's application connectivity product, built on Kuadrant. It provides the Gateway API implementation that the MCP Gateway routes traffic through, and it ships the Kuadrant policy engines — the `AuthPolicy` and `RateLimitPolicy` resources to enforce authentication, authorization, and rate limits.

Start by creating the GatewayClass, which tells the cluster which controller implements Gateway API resources:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: openshift-default
spec:
  controllerName: openshift.io/gateway-controller/v1
EOF
----

Then, install the Connectivity Link operator:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: kuadrant-system
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: kuadrant
  namespace: kuadrant-system
spec:
  upgradeStrategy: Default
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: rhcl-operator
  namespace: kuadrant-system
spec:
  channel: stable-1.5
  installPlanApproval: Automatic
  name: rhcl-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF
----

Wait for the operator installation to complete:

[source,bash,role="execute"]
----
until oc get csv -n kuadrant-system -l operators.coreos.com/rhcl-operator.kuadrant-system="" -o name 2>/dev/null | grep -q .; do
  echo "Waiting for the operator CSV to be created..."
  sleep 10
done
oc wait csv -n kuadrant-system -l operators.coreos.com/rhcl-operator.kuadrant-system="" --for=jsonpath='{.status.phase}'=Succeeded --timeout=600s
----

The operator manages instances of the `Kuadrant` custom resource. Creating one is what actually installs the data plane and the policy engines:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: kuadrant.io/v1beta1
kind: Kuadrant
metadata:
  name: kuadrant
  namespace: kuadrant-system
spec: {}
EOF
----

Wait for the Kuadrant instance to become ready:

[source,bash,role="execute"]
----
oc wait kuadrant/kuadrant --for="condition=Ready=true" -n kuadrant-system --timeout=600s
----

[#deploy-mcp-gateway]
== 4. Deploy the MCP Gateway

With Connectivity Link in place, the MCP Gateway is ready to be deployed. In Connectivity Link 1.5, the `Kuadrant` custom resource you just created deploys the MCP Gateway controller automatically: the `mcp-gateway-controller` pod runs in the `kuadrant-system` namespace. Confirm that the controller is running:

[source,bash,role="execute"]
----
until oc get deployment/mcp-gateway-controller -n kuadrant-system >/dev/null 2>&1; do
  echo "Waiting for the MCP Gateway controller to be created..."
  sleep 10
done
oc wait --for=condition=Available deployment/mcp-gateway-controller -n kuadrant-system --timeout=300s
----

Now create the `Gateway` and the `MCPGatewayExtension` that activates the gateway on it. The design is worth understanding before you apply it:

* The `mcp` listener has the gateway's own hostname and serves the *broker* — the endpoint that MCP clients like OpenShift Lightspeed talk to. The broker presents the combined tool catalog of every registered server and forwards each tool call to the right one.
* The `mcps` listener is a wildcard listener where every registered MCP server attaches with its own hostname, keeping each server's traffic on its own route.

The `MCPGatewayExtension` ties the two together on the `mcp` listener and manages the HTTPRoutes the gateway needs:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: mcp-system
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: mcp-gateway
  namespace: mcp-system
  annotations:
    networking.istio.io/service-type: ClusterIP
spec:
  gatewayClassName: openshift-default
  listeners:
    - name: mcp
      hostname: mcp-gateway-openshift-default.mcp-system.svc.cluster.local
      port: 8080
      protocol: HTTP
      allowedRoutes:
        namespaces:
          from: All
    - name: mcps
      hostname: "*.mcp.internal"
      port: 8080
      protocol: HTTP
      allowedRoutes:
        namespaces:
          from: All
---
apiVersion: mcp.kuadrant.io/v1
kind: MCPGatewayExtension
metadata:
  name: mcp-gateway-extension
  namespace: mcp-system
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: Gateway
    name: mcp-gateway
    namespace: mcp-system
    sectionName: mcp
  httpRouteManagement: Enabled
  privateHost: http://mcp-gateway-openshift-default.mcp-system.svc.cluster.local:8080
EOF
----

Wait for the extension to become ready:

[source,bash,role="execute"]
----
oc wait --for=condition=Ready mcpgatewayextension/mcp-gateway-extension -n mcp-system --timeout=300s
----

Connectivity Link also ships a console plugin that gives the gateway a face in the OpenShift web console. Enable it:

[source,bash,role="execute"]
----
oc patch console.operator.openshift.io cluster --type json \
  -p '[{"op":"add","path":"/spec/plugins/-","value":"kuadrant-console-plugin"}]'
----

The OpenShift web console reloads automatically. Log in again:

* *Username:* `{openshift_cluster_admin_username}`
* *Password:* `{openshift_cluster_admin_password}`

A *Connectivity Link* section appears in the navigation menu. Its *MCP management* pages list the gateway extensions, the registered MCP servers with their online status, and the attached policies. The *MCP Inspector* lets you validate and run individual tools directly — useful for testing a tool without going through the assistant.

Take a moment to explore the *Connectivity Link* -> *MCP management* pages before moving on. Right now the lists are mostly empty; as you register servers in the next section and attach policies in the next modules, come back here to watch the gateway fill up.

[#register-mcp-server]
== 5. Register the MCP server

The MCP server is running, but the gateway does not know about it yet. Registration is a two-step dance:

1. An `HTTPRoute` labeled for discovery exposes the server's Service on the gateway's wildcard `mcps` listener. Each server gets a hostname of its own, because the gateway routes the broker and every registered server by Host header. If a server shared the broker's hostname, its tool calls would land on the broker's route instead.
2. An `MCPServerRegistration` tells the gateway's broker about the server: where to reach it, which prefix to put in front of its tool names (so tools from different servers never collide), a category, and a hint that helps LLM clients pick the right tool.

Apply both:

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: openshift-mcp-server
  namespace: mcp-servers
  labels:
    mcp-server: 'true'
spec:
  hostnames:
    - openshift-mcp-server.mcp.internal
  parentRefs:
    - group: gateway.networking.k8s.io
      name: mcp-gateway
      namespace: mcp-system
      sectionName: mcps
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /mcp
      backendRefs:
        - name: openshift-mcp-server
          port: 8080
---
apiVersion: mcp.kuadrant.io/v1
kind: MCPServerRegistration
metadata:
  name: openshift-mcp-server
  namespace: mcp-servers
spec:
  prefix: openshift_
  path: /mcp
  category:
    - openshift
  hint: >-
    Inspect and manage OpenShift cluster resources — pods, workloads, nodes,
    events, and configuration.
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: openshift-mcp-server
    namespace: mcp-servers
EOF
----

The broker connects to the server and discovers its tools. Wait for the registration to report them:

[source,bash,role="execute"]
----
oc wait --for=condition=Ready mcpsr/openshift-mcp-server -n mcp-servers --timeout=300s
oc get mcpsr -n mcp-servers
----

The registration shows as *Ready*. In the web console, the *Connectivity Link* -> *MCP management* pages now list `openshift-mcp-server` with its online status and its catalog of `openshift_`-prefixed tools — the same tools the built-in server exposed in the cluster interaction module, now served through the gateway.

[#configure-ols]
== 6. Point OpenShift Lightspeed at the gateway

The last step is to rewire OpenShift Lightspeed: instead of the built-in MCP server, the assistant should use the gateway's broker as its MCP server. Two details in this configuration do a lot of work:

* The `Authorization` header is set with `valueFrom: kubernetes`, so OpenShift Lightspeed forwards the logged-in user's bearer token on every tool call.
* `introspectionEnabled` is set to `false`, which shuts down the operator-managed OpenShift MCP server. Its tools would otherwise appear twice: once directly, once federated through the gateway with the `openshift_` prefix.

Apply the change:

[source,bash,role="execute"]
----
oc patch olsconfig cluster --type merge -p '{"spec":{"featureGates":["MCPServer"],"ols":{"introspectionEnabled":false},"mcpServers":[{"name":"mcp-gateway","url":"http://mcp-gateway-openshift-default.mcp-system.svc.cluster.local:8080/mcp","timeout":30,"headers":[{"name":"Authorization","valueFrom":{"type":"kubernetes"}}]}]}}'
----

The operator picks up the change and rolls out the OpenShift Lightspeed app server pod with the new configuration. Wait for the Ready status before using the assistant:

[source,bash,role="execute"]
----
oc rollout status deployment/lightspeed-app-server -n openshift-lightspeed --timeout=300s
oc wait olsconfig cluster --for=jsonpath='{.status.overallStatus}'=Ready --timeout=600s
----

Once the app server is running, the intelligent assistant discovers the tools of every MCP server registered behind the gateway, prefixed with the registration prefix. Time to see the federation in action: switch to the *Console* tab, open the chat interface, click *Clear chat*, and ask a question that requires cluster introspection:

[source,role="copypaste"]
----
Show me the pods running in the lightspeed-demo namespace.
----

The assistant calls the `openshift_pods_list` tool — notice the `openshift_` prefix. Every tool call behind that answer traveled through the gateway's broker, which forwarded it to the registered MCP server.

The same pattern scales to any MCP server you register later: deploy it, route it, register it, and its tools appear in the assistant's catalog with their own prefix — no OpenShift Lightspeed reconfiguration required beyond the single gateway entry.

[#whats-next]
== 7. What's next?

The gateway now federates the MCP server's tools behind a single endpoint, and the assistant uses it. But take a closer look at what is actually enforced: the gateway accepts *any* request that reaches it. Nothing yet checks who is calling, which tools they may use, how fast they can call them, or what content flows through.

That is the job of the next two modules:

* xref:module-13.adoc[Gateway Authentication and Authorization] federates the cluster login to Keycloak to get distinct user personas, then requires a valid OpenShift token on every tool call, authorizes individual tools with Kubernetes RBAC, applies per-user rate limits, and wires up distributed tracing so you can watch every tool call end to end.
* xref:module-14.adoc[Gateway Guardrails] adds content inspection of tool calls and responses with NeMo Guardrails, and finishes with an end-to-end test that puts every layer — federation, authentication, authorization, rate limiting, tracing, and guardrails — through its paces.
